# 项目说明：南瓜厨房

## 想解决的问题

当一个人想邀请自己熟悉的 AI 一起玩游戏时，仅有聊天建议还不够：AI 需要看见同一局面、拥有自己的角色、执行会影响游戏的动作，并且能够在用户接管或停止时交还控制。

南瓜厨房用一个短局协作场景实现这件事。用户和 AI 分别操作一个角色，共同接单、取材、切配、烹饪和交付。项目重点是“人与自己的 AI 共同参与”，厨房是这一体验的具体载体。

## 本次交付范围

| 项目 | 内容 |
|---|---|
| 一局玩法 | 约 90 秒，订单倒计时、两种菜谱、交付、计分和结算 |
| 人类操作 | 键盘移动、点击前往、互动按钮、队友接管 |
| 规则演示 | 明确标注的演示队友，用于网页即时试玩和熟悉操作 |
| 真实 AI 接入 | 完整本地版通过 MCP 暴露规则、观察、席位与语义任务 |
| 交接资料 | 面向使用者的说明，以及可直接交给 AI 执行的本地接入指南 |

网页试玩只运行规则演示模式。真实 AI 配合通过本地完整版本体验，演示视频应使用实际接入录像予以说明。

## 实现思路

游戏规则与渲染分开：规则模块处理物品、订单、工位、动作和时间；界面呈现实际快照并收集玩家输入。完整本地版由服务端持有权威游戏状态，MCP 与网页操作进入同一套规则。

AI 不负责毫秒级按键控制。它选择“前往工位并完成指定操作”这样的任务，由游戏执行移动与加工；执行结果再返回给 AI。这降低了模型请求往返与游戏帧率之间的耦合。

网页试玩复用游戏规则，在浏览器内独立运行演示实例。它与本地 MCP 房间互不相连，也不包含用户私有的网络或账号配置。

## 交互与控制边界

- 人类和 AI 各有独立席位；AI 只能控制自己取得的席位。
- 动作绑定当前回合、状态与控制上下文，过期或失效的请求应被拒绝。
- 用户可以接管队友；AI 失去控制后停止，不自动抢回。
- 连接 AI 席位后停在大厅，由用户开始游戏；新回合重新取得控制上下文。
- 规则演示与真实 AI 使用明确标签区分，不以演示脚本冒充模型操作。

## 已知限制

模型思考、工具审批与请求延迟会带来动作间空档。当前项目没有后台托管 AI、跨设备多人房间、语音服务或模型 API 代理。

完整本地版首次需要安装运行环境和依赖。支持本地操作的 AI 可以按照指南协助完成；云端客户端还需要使用者自己的受保护连接。

## 后续方向

在现有体验稳定、确有需要时，探索让人和自己的 AI 在现成网页小游戏中共同游玩。这是后续方向，不作为本次已经完成的功能。
